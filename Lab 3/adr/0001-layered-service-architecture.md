# ADR 0001: Виділення сервісного шару та ізоляція логіки ціноутворення у PricingService

* **Статус:** Прийнято (Accepted)
* **Дата:** 2026-10-15
* **Контекст проєкту:** OpenCRM — Динаміка взаємодії та Sequence Diagram (Lab 3)

---

## 1. Контекст та постановка проблеми
Сценарій оформлення угоди (`UC-2`, `UC-3`, `UC-4`, `UC-5`, `UC-6`) включає складну послідовність кроків:
1. Перевірка доступності та активності товарів у каталозі (`Product.is_active`).
2. Фіксація транзакційної ціни `actual_price` для позицій `DealItem`.
3. Розрахунок проміжної суми специфікації.
4. Перевірка порогової умови надання опціональної знижки до 15% (вимога `EARS-OPT-01`: сума $> 100\,000$ грн або VIP-клієнт).
5. Атомарне оновлення загальної вартості угоди (`Deal.total_amount`).
6. Відправка комерційної пропозиції клієнту через зовнішній `EmailService`.

Необхідно обрати архітектурний підхід для розподілу цих обов'язків між компонентами бекенду OpenCRM.

---

## 2. Розглянуті альтернативи

### Варіант 1: «Товстий контролер» (Smart Controller / Transaction Script)
* **Плюси:** Менша кількість класів/файлів на початковому етапі.
* **Мінуси:**
  * Змішування HTTP-транспорту (заголовки, статус-коди) з доменною логікою розрахунку знижок.
  * Неможливість перевикористати логіку ціноутворення для інших каналів (наприклад, фонових скриптів або консольних утиліт).
  * Складність юніт-тестування фінансових калькуляцій.

### Варіант 2: Багаторівнева сервісна архітектура (DealService + PricingService)
* **Плюси:**
  * **Single Responsibility:** `PricingService` відповідає виключно за математику, порогові знижки та підсумкову вартість; `DealService` відповідає за оркестрацію процесу та координацію збереження даних.
  * **Ізоляція доменної логіки:** Бізнес-правила не залежать від Fastify/Express контролерів чи конкретного ORM.
  * **Висока тестованість:** `PricingService` тестується чистими юніт-тестами без підняття БД.
* **Мінуси:** Потребує введення додаткового інтерфейсу сервісу.

---

## 3. Прийняте рішення
Обрано **Варіант 2: Багаторівнева сервісна архітектура з виділенням `PricingService`**.

* `DealController` приймає HTTP DTO та делегує обробку `DealService`.
* `DealService` завантажує актуальні товари через `ProductRepository`, передає список на розрахунок у `PricingService`, зберігає результат через `DealRepository` та асинхронно викликає `EmailService`.
