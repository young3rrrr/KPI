## 1. Слід запитів до ШІ (AI Prompts Trail)

### Початковий системний запит (Prompt 1 — Baseline Generation):
```text
Створи специфікацію вимог та модель прецедентів для системи OpenCRM.
Вимоги:
1. Текстові вимоги у 3 нотаціях:
   - EARS (Ubiquitous, Event-driven, State-driven, Unwanted behavior, Optional features).
   - User Stories (As a ... I want ... so that ...).
   - Gherkin-сценарії (Given ... When ... Then ...).
2. Діаграма прецедентів (Mermaid):
   - Мінімум 2 типи акторів (людина: SalesManager, зовнішні: EmailService, SchedulerService).
   - Зв'язки: <<include>>, <<extend>>, генералізація.
3. Матриця трасування (Traceability Matrix):
   - Зв'язки M:N (багато-до-багатьох) між вимогами, сценаріями та тестами.
   - Наявність мінімум 1 усвідомлено непокритої вимоги з обґрунтуванням.
4. Контекст: сутності з Lab 1 (User, Lead, Client, Deal, Product, DealItem, Activity).
```

## 2. Аудит помилок ШІ (Top-3 AI Errors Chain)

Згідно з регламентом Definition of Done, кожна помилка зафіксована за обов'язковим ланцюжком:
$$\text{Промпт} \longrightarrow \text{Згенерована помилка} \longrightarrow \text{Фідбек-коригування} \longrightarrow \text{Зміна специфікації}$$

---

### Помилка 1: Некоректне застосування `<<extend>>` для обов'язкового розрахунку суми (D-01)
* **Початковий промпт:** «...додай прецедент розрахунку підсумкової вартості угоди при її веденні».
* **Згенерована помилка ШІ:** Модель зв'язала базовий прецедент `UC-2 (Ведення угоди)` та `UC-4 (Розрахунок підсумкової суми)` зв'язком `<<extend>>`. Це порушує семантику UML, оскільки робить розрахунок суми необов'язковим/умовним розширенням, тоді як жодна угода не може бути сформована без фіксації вартості.
* **Фідбек-коригування:** «Розрахунок вартості є обов'язковою частиною життєвого циклу угоди. Заміни зв'язок на `<<include>>`, оскільки базовий прецедент не може завершитися без виконання включеного».
* **Зміна специфікації (`spec.md`):** Уточнено критерій `AC-02` (обов'язковість включення розрахунку вартості через `<<include>>`). Зафіксовано комітом у Git.

---

### Помилка 2: Трівіальне зіставлення 1:1 у матриці трасування (D-02)
* **Початковий промпт:** «...побудуй матрицю трасування вимог EARS, сценаріїв та тестів».
* **Згенерована помилка ШІ:** Модель створила спрощену таблицю з прямою відповідністю 1:1 (кожна вимога вела строго до одного сценарію та одного тесту).
* **Фідбек-коригування:** «Згідно з критеріями оцінювання Завдання 2, зв'язки в матриці трасування повинні бути типу M:N (багато-до-багатьох), де одна комплексна EARS-вимога покривається декількома сценаріями/тестами, а один сценарій верифікує декілька вимог».
* **Зміна специфікації (`spec.md`):** Перероблено матрицю трасування на повноцінне відношення $M:N$, додано критерій `AC-05`. Зафіксовано комітом у Git.

---

### Помилка 3: Відхилення від доменної термінології Завдання 1 (D-03)
* **Початковий промпт:** «...опиши додавання товарних позицій до угоди та планування завдань менеджера».
* **Згенерована помилка ШІ:** Модель використала загальні терміни `OrderItem` (замість сутності `DealItem` з ER-діаграми Lab 1) та `CRMTask` (замість сутності `Activity`). Це порушило вимогу наскрізного ланцюга моделей.
* **Фідбек-коригування:** «Усі сутності в User Stories та Use Cases мають строго збігатися з моделлю даних із Завдання 1: сутність позиції угоди називається `DealItem`, сутність взаємодій — `Activity`».
* **Зміна специфікації (`spec.md`):** Гармонізовано термінологію у всіх EARS-вимогах, User Stories та діаграмі прецедентів (критерій `AC-06`). Зафіксовано комітом у Git.
